**Дубликат 10042 / 10044 уже подавлен осознанно:**

```ts
export const HIDDEN_DUPLICATE_RESOURCE_SHOP_ITEM_IDS = new Set<number>([10042, 10044]);
```

Магазин ресурсов скрывает `10042 Gold Bar` и `10044 Gold Nugget`, оставляя
игроку один канал покупки золота. `10044` при этом живёт в `data/buildings.ts`
как дроп построек (`Самородок`) — это осознанное разделение: **дроп есть,
покупки нет**.

**Вывод:** не «чинить» дубликат удалением предмета. 10042/10044 удалены из
витрины, и это работает. Любая новая механика обязана уважать
`HIDDEN_DUPLICATE_RESOURCE_SHOP_ITEM_IDS`.

## 2. Экономический инвариант (главный страж перед Steam)

Существующий `tests/economy/early-housing-balance.mjs` проверяет стоимость
`1000 / 1001 / 1002` в раннем прогрессе. Его нужно расширить до **инварианта
суммарного потока**, а не только ценников.

### Инвариант I-1: источник золота единственный

```
gold_delta_за_игровой_день = Σ(рынки NPC) + Σ(квесты) + Σ(монстры)
gold_delta_за_день − Σ(разрешённые_источники) === 0
```

Реализация: в тесте пройтись по всем `data/buildings.ts` и `data/items.ts`,
найти все записи, дающие `gold` или `ruby`, и сверить с белым списком.
Любая новая постройка/предмет вне списка → тест падает.

### Инвариант I-2: Ruby не имеет нового пути эмиссии

`ruby` остаётся только покупкой за реальные деньги (`payments.ts` →
`steam.ts`). Тест ищет в коде все присвоения `ruby` и запрещает новые.

### Инвариант I-3: золотые формы не конвертируются взаимно

`10039 Gold Dust`, `10042 Gold Bar`, `10044 Gold Nugget` не должны
превращаться друг в друга или в `gold` напрямую. Если конверсия нужна —
только через переработку на заводе с потерей (например 3 Dust → 1 Bar).

Тест обязан проверять, что `HIDDEN_DUPLICATE_RESOURCE_SHOP_ITEM_IDS`
остаётся `{10042, 10044}` и что ни одна новая механика (биржа, дорога) не
возвращает эти предметы в витрину или в обмен.

### Инвариант I-4: цена покупки ≥ себестоимость

Ни одна новая механика не даёт предмет дешевле, чем стоимость его
производства из базовых ресурсов. Иначе появляется бесконечный цикл.

**Формула проверки:**
```
cost(item) ≤ Σ cost(ingredients) × (1 − margin_min), margin_min = 0.10
```

## 3. Приоритет B.1 — Железная дорога

### Что уже подходит по архитектуре

`data/buildings.ts` содержит категорию `Дороги и стены` (10 построек) —
дорожная сеть в проекте уже есть. Железная дорога строится как ещё один
её элемент, а не как новая система.

### Модель (без новой нагрузки на PocketBase)

```mermaid
flowchart LR
  A[Игрок строит Вокзал] --> B[Локальный seed + UTC-время]
  B --> C[Детерминированное расписание на клиенте]
  C --> D[Поезд прибывает: слоты доставки]
  D --> E[Игрок отправляет ресурсы через существующий inventory pipeline]
  E --> F[Обычный market-запрос, никаких новых таблиц]
```

**Расписание поездов не хранится в БД.** Оно вычисляется из
`floor(unix_time / interval)` — та же схема, что уже используется для
`marketStaticData` (статические цены, без записи в БД).

### Экономика: скидка, не эмиссия

Дорога даёт **скидку на логистику**, а не золото:
```
цена_доставки_поездом = базовая_цена × (1 − 0.15 × уровень_вокзала)
```
Ограничение: скидка применяется только к предметам `10000–10019`
(базовые ресурсы) и `10032–10037` (сельхоз), **не** к военным
`10021–10025` и **не** к золотым `10026–10030`, `10039–10045`.

### Что нужно проверить перед реализацией

| Вопрос | Где искать ответ |
|---|---|
| Как хранится позиция постройки | модель `buildings` в PocketBase |
| Есть ли уже понятие дистанции между игроками | `src/game/` и `pb_hooks/main.pb.js` |
| Как считается текущая цена доставки | `src/game/market/marketLogic.js` → `calculateMarketPrice` |

### Тесты для дороги (новые сценарии)

- `scenario-29-railway-schedule.mjs` — одинаковый seed даёт одинаковое расписание у двух клиентов
- `scenario-30-railway-discount.mjs` — скидка не применяется к военным и золотым предметам
- `scenario-31-railway-no-emission.mjs` — после цикла отправки суммарный `gold` не вырос

## 4. Приоритет B.3 — Биржа

### Модель

`marketStaticData.ts` уже содержит статические цены без записи в БД.
Биржа — надстройка над этим слоем: **детерминированный псевдослучайный
индекс** вместо новых таблиц.

```
price(item, t) = base_price(item) × (1 + amplitude × wave(item, t))
wave(item, t)  = sin(hash(item_id, floor(t / 3600)) normalized to [-1, 1])
```

Ключевое: `floor(t / 3600)` — часовой такт. Все клиенты в один час видят
одну и ту же цену, при этом **ни один клиент ничего не пишет в БД**.

### Ограничение амплитуды

`amplitude = 0.25` максимум. Причина: при большей амплитуде появляется
арбитраж между биржей и фиксированным NPC-рынком. NPC-цены остаются
фиксированными якорем — именно они не дают бирже разогнать инфляцию.

### Опциональный серверный снапшот (только если понадобится)

Если позже потребуется, чтобы цены зависели от реального объёма торгов:
1. `pb_hooks/main.pb.js` — cron-хук раз в 15 минут пишет один документ
   в коллекцию `market_snapshot` (одна запись на весь мир, не на игрока).
2. Клиенты читают этот единственный документ и локально интерполируют.

Утилита уже есть: `pb_hooks/tree_server_utils.js` (136 строк) — тот же
паттерн серверного снапшота.

**Нагрузка:** 4 записи в час на весь сервер. Это пренебрежимо.

### Тесты для биржи

- `scenario-32-exchange-determinism.mjs` — два клиента с одним seed получают идентичные котировки
- `scenario-33-exchange-amplitude.mjs` — ни одна котировка не выходит за ±25 % базы
- `scenario-34-exchange-no-arbitrage.mjs` — купить на бирже → продать NPC = убыток ≥ 5 %
